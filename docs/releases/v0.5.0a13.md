# R48Display v0.5.0a13 — alpha (arduino-esp32 3.1)

**Pre-release for hardware testing** — install over **USB**.

After the a12 "BLE worker task" boot-looped, this build steps back to the **proven
approach** instead of iterating on the worker. It keeps a11's coexistence-aware
BLE — async **passive** scan via NimBLE callbacks, matched by *advertised* service
UUID, gated on a stable WiFi link — and adds the one documented coexistence guard
it was missing.

## Why not the worker task
Moving BLE into its own FreeRTOS task (a12) isn't wrong, but it isn't required:
NimBLE already runs its own host task, and the NimBLE-Arduino `NimBLE_Client`
example (and the maintainer's guidance) is exactly a11's pattern — an async scan
callback that flags a match, with the connect performed *outside* the callback.
a12's crash was most likely its **8 KB worker-task stack** overflowing during
connect + service discovery, not the architecture itself.

## What changed
- **BLE now initializes only under WiFi `MIN_MODEM` power-save.** Per NimBLE-Arduino
  issue #437 and Espressif's RF-coexistence guide, bringing up the BLE controller
  while WiFi modem-sleep is off (`WIFI_PS_NONE`, which the setup AP uses) is
  documented to crash under coexistence on core 3. a13 forces `MIN_MODEM`
  immediately before `NimBLEDevice::init()`.
- Everything else from a11 is retained: `MIN_MODEM` hold on core 3 (a7),
  non-blocking async scan (a8), bounded manual scan (a9), BLE paused if scans
  starve WiFi (a10), and the `[WiFi]`/`[BLE]` serial diagnostics.

## What a test tells us next
The BLE scan is **passive** (coexistence-friendly) and matches the BMS by its
**advertised service UUID**. If your BMS only puts its name in the scan *response*,
a passive scan can't see it. The serial log answers this directly:

- `[BLE] BMS scan: N seen` — if **N is 0** with WiFi stable, the next proven step is
  to switch *all* scans to **active** (done consistently, to avoid the
  active-after-passive crash — NimBLE #402). If **N > 0**, it's a match-logic issue,
  not a scan issue.

Install a13, let WiFi settle for a minute, then capture the serial log (115200) —
the `[BLE]` scan counts tell us exactly which proven change comes next.
